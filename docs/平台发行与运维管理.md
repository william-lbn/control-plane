# 平台发行与运维管理

状态：当前设计合同，2026-11-07；已实现项与计划项分开。[总方案](平台总方案与演进规划.md)为当前入口。

## 1. “是否是真实 Neon”如何核实

我们运行的是基于 Neon/Autoscaling 和 PostgreSQL fork 的自有发行，加入已验收的内存增强；不应把 `postgres:18` 标签、镜像仓库名或网站截图当来源证明。

| 核对层 | 最小记录和校验 | 结果含义 |
|---|---|---|
| 源码 | 各仓库原 URL/commit、Neon PG gitlink、实际参与构建的 PG commit、补丁差异 | 能追到上游和自有修改；分支最新 HEAD 不必等于旧发行源码，必须精确记录 |
| 构建 | Dockerfile/上下文摘要、工具链、PG configure、扩展与 WAL redo 配套版本、基础镜像 digest、SBOM/provenance | 不只证明“能编译”；含完整运行依赖，尤其各 PG 大版本 neon_walredo |
| 制品 | OCI index/平台 manifest/config digest 分开，架构、签名/可信发布者、归档位置 | Docker image ID 不等于多架构索引或运行 manifest；不能混作同一 SHA |
| 部署 | Helm 渲染/values摘要、Pod spec、containerd imageID、Guest rootDisk digest、节点 | 证明实际运行发行；Runner 镜像不能替代 Guest 镜像 |
| 运行 | SQL server_version_num、扩展版本/加载、管理能力、对应 Timeline PG 版本、真实数据/内存动作 | 证明运行合同；SELECT version() 不能单独证明整个供应链 |

## 2. 发行目录不是租户任意镜像输入

现有候选 `NEON_DSGA_RUNTIME_CATALOG` 只供受信平台进程配置；一个选项选择 PG 大版本/区域并冻结完整计划。旧单版本配置兼容、旧计划不变；新目录要求明确 PG17/18 与原生硬预算协议 v3。公开 capabilities 只投影产品选项、范围、memory scaling 能力和开关，不泄漏 Service UID/镜像/秘密来源。

后续发行信息扩展原有配置和持久操作，不立刻再造中心。每份不可变发行记录包括：

- release ID、schema、生命周期（candidate/validated/stable/deprecated/blocked）、来源提交与构建证据；
- CP/Agent/Runner/Guest/Neon/Pageserver/扩展/基础 OS 的精确兼容集合，不把共享组件按租户重复部署；
- PG full version/major、协议与可选能力、资源 profile、宿主/Guest要求和已验证规格；
- 镜像 digest、Helm/schema、元数据库 migration范围、配置模板摘要、必要的 Secret 引用类型；
- 精确本地/三节点E2E证据，维护方式、已知限制、停止推广条件和恢复方法。

生命周期在首次实现中可以由版本化仓库清单及受控发布流程承担，后续运营 API/UI 管理同一对象；不得出现文件目录和数据库目录两套互相矛盾的权威。配置对象校验成功不自动等于 validated，更不能由项目请求自报“已验收”。

## 3. 配置职责与持久化

| 类型 | 来源/存放 | 写者和变更方式 |
|---|---|---|
| 租户期望 | 原项目/服务/策略表、Operation | 有权限租户，版本 CAS、幂等、配额和审计 |
| 平台发行/区域/供应商 | 受控配置及现有平台模型 | 明确平台角色；验证→发布→观察，保留前版 |
| 部署配置 | 自有 Helm/ConfigMap/Secret refs | 受控发行；不由租户写 Kubernetes spec |
| 实际状态 | 原组件只读观察与元数据库投影 | 原 Driver；带 observed generation、时间与来源，陈旧标记不填假值 |
| 秘密 | K8s Secret/已有加密存储与独立密钥管理 | 定向最小读取，轮换代次和审计；不进日志、普通配置、URL或提交 |
| 业务/系统数据 | 项目 Timeline；独立 CP/Controller 元数据 | 数据恢复与应用生命周期解耦，不能因删除一个项目删除平台库 |

配置 API 返回脱敏值、来源、修订、应用状态和错误。平台管理员也不应默认读取用户密码、供应商总密钥或数据库内容。有效配置与期望配置分开，日志关联 request/operation/resource，不输出全部 env/Secret。

## 4. 运维入口复用与缺口

已确认源码：`platform_policy.go` 的独立平台角色、`/platform/ai-providers`、`/platform/ai-credits`、`/platform/service-plans`、`/platform/billing`、`/platform/storage-gc`；React 已有相应部分界面。组织 Admin/应用 Auth Admin/平台 Operator 是不同身份。

需按阶段补齐：发行只读清单与 drift 观察、维护窗口/升级操作、配置修订与生效观察、故障 Operation 的受限恢复入口、容量和证书到期告警、元数据库/Secrets/对象/WAL 的可恢复备份。首先连实际已有过程，不增加“任意集群命令”API。恢复操作记录原因、操作者、目标UID/代次、前置和结果；不重置旧账本伪装新实例。

租户入口与平台入口可共享前端应用，路由、服务端授权、菜单与能力投影分离即可；暂不为两个入口复制整套前后端。将现有分散 platform policy 收敛为共同权限检查时保持原权限上界，不能把“有供应商权限”等同于“可升级数据库”。

## 5. 升级分类与回退

| 变更 | 必查差异 | 实施原则 |
|---|---|---|
| PG minor/security | 发布说明、补丁冲突、扩展 ABI/SQL、WAL redo、内存增强回归 | 同大版本候选，与新 Guest 完整依赖一同验证；通过维护/冷醒交付，不悄改运行进程 |
| PG major | 内核适配、存储/WAL/扩展/Guest能力、新项目迁移 | 共用上层接口；新项目验证后切换连接，不直接指向旧主版本数据 |
| Neon/Pageserver/Safekeeper | API、WAL、对象/存储格式、所有支持 PG redo | 先识别官方支持滚动/混合组合，再规划顺序；不能凭版本号假定可混跑 |
| Autoscaling/Runner/Guest | 协议协商、持久动作/预算、恢复/fencing、kernel/QEMU | 先兼容读者再启用生产者；Unknown/已提交动作保留原身份与执行结果 |
| CP/元数据库 | additive schema、旧Worker/新Worker合同、权限/幂等 | 前向迁移、独立测试、限制活动写者；旧计划可恢复 |
| OS/依赖/基础镜像 | CVE、libc/OpenSSL/内核能力、二进制运行依赖 | 只重建受影响制品，真实启动/相关链验证，记录 digest 与差异 |
| 扩展 | 共享库及SQL extension版本、索引格式、升级脚本 | 镜像包含新库不等于客户库已ALTER EXTENSION；单列实际安装与升级结果 |

推广步骤：固定源码→增量构建→供应链/依赖检查→组件回归→PG17/18真实共同场景→小范围维护→全平台推广→现场反查。执行变更前读回活动动作，停止新的冲突操作并等待/恢复原操作，不能用“重启会修好”绕过未决账本。

镜像回退只在软件/数据格式确实兼容时可用；不支持数据降级就保留原数据，使用已演练的备份恢复或前向修复。目标维护时间和实测中断时间分开记录；不宣传没有验证的零停机。

## 6. 长期演进与最小改动策略

- 常态跟踪 PostgreSQL、Neon、Autoscaling、依赖和 OS 的发布/安全通告；固定来源 SHA，先评估相关差异，不每天追 main 重建生产。
- 发布说明标记新增、修复、废弃、已知限制和受影响服务；按环境配置服务区域，不硬编码官方 AWS 区域。
- 保持共同版本化 API、spec/status、发行能力协商和兼容测试，PG版本差异封装在内核适配/打包层。
- 若上游实现等价能力，先对现有安全 normal、恢复与应用数据合同做替代验证，再删除冗余自有补丁；不为了“抽象先进”增加没消费者的通用协议层。
- API兼容、数据库迁移、镜像供应链与数据可恢复性是长期平台治理，不是额外分配器或硬件证明。分阶段实现，第一关键路径仍是 C1。

当前最新安全补丁是否齐全仍需逐发行核对；PG18现场读回曾为 18.2，不应标记“等同官网当前最新版”。本轮暂不未经兼容验证替换已验收核心；生产发行前列出实际差异及处理结论。

现场labels仍包含 `io.neon.build.scope=initial-environment-pg17-not-production` 与早期Autoscaling revision。这是继承标签的发行缺口，不能将其当成PG18最终源码锁。保留已验收digest及原始构建/失败证据；后续构建用已提交的可复现配方显式写入所有实际组件版本、构建输入及准确digest，核运行回读后才推广。禁止只改tag/label来伪造已验收发行；新的digest需要针对变化重新验收。当前总方案不承诺官方云与自建镜像相同。

管理配置同样属于发行输入：controller现场仍为开发HTTP模式，尚无Compute ClusterIssuer；必须接通原生TLS/JWT、调用方及轮换路径后才能放行管理面。不能把本轮内存功能通过改写为整个平台已具备生产安全配置。
