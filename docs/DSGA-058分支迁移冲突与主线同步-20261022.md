## 为什么不能直接合并两个 058

主线已有 `058_catalog_current_observations.sql`，此前 DSGA 功能分支已发布
`058_dsga_creation_identity.sql`。原登记器只以 integer 为主键，按文件名排序后
第二份同号文件会静默跳过。Git 没有文本冲突不等于数据库迁移正确。

两份已发布 058 保留原字节，未重命名、改编号或加 IF NOT EXISTS 掩盖历史。
追加 `900000059_dsga_creation_and_catalog_058_join.sql`：在原迁移事务内补齐
缺失的**整份原始 DDL**。新库、原主线058、原DSGA058最终都具备两份功能，
已有表不 DROP/重建，不 UPDATE/清空原行。不存在的表才执行对应原DDL；存在
但关键列/原键/引用/不可变触发器缺失或被禁用时拒绝，整个事务回滚。

这是针对已知历史冲突的前向修复，不是运行任意同号文件的通用机制。新登记器
在执行文件前审核完整 registry：仅上述两份058且配套join存在时允许，其他重复/
非法integer编号全部失败关闭。DSGA后续迁移使用900000000以上的独立保留段
（仍在既有int32范围），避免普通主线继续059、060时反复碰撞。每轮主线若修改
共同生命周期函数，仍须审查并做新的前向语义合并，不能仅依据编号自动盖过。

原 schema_migrations 的058行及 applied_at 保留；新增高位行记录两份功能已完成
前向合流，不伪造“原来就分别执行过两个058”的历史。FreshSchema测试按已审查的
唯一同号对核对 distinct 数字登记数，运行时registry同时拒绝其他同号遗漏。

原DSGA058并记录旧数字历史，然后调用生产 migrate 两次；不是在新schema删表
冒充旧版本。三种来源都升级成功；两种旧来源还种入真实FK审计/UID行，验证
