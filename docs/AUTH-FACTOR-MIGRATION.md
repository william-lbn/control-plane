# Auth 分支 TOTP 迁移

控制面 0.72 增加 `inherit_two_factor: true`。这是启用物理子分支 Auth 时的显式选择，必须同时启用 `two_factor_enabled`。父分支由控制面的实际分支关系确定，客户端不能提供父分支密钥或另一个来源分支。默认请求、既有 Operation 的五个步骤及请求哈希保持兼容。

## 操作流程

1. 在子分支的 Auth 页面选择原 Auth 数据库，开启 TOTP，并勾选“迁移父分支双重认证”，然后启用 Auth。
2. 用户以原密码登录，使用原验证器完成第二步验证。密码验证通过后仍不会提前建立会话或签发 JWT。
3. 用户登录后生成并保存子分支的新恢复码。父分支恢复码在子分支失效；父分支保留自己的恢复码。

若自动继承的 Auth 已因已绑定验证器而受保护地停止，需要先禁用该子分支 Auth，再显式勾选迁移并启用。原失败 Operation 的请求内容不会被改写。

```json
{
  "database": "application_database",
  "allowed_origins": [],
  "two_factor_enabled": true,
  "inherit_two_factor": true
}
```

沿用项目/分支 Auth 的 POST 接口、`If-Match` generation 和 `Idempotency-Key`。根分支不能指定继承。已有实例的数据库仍不可改名或切换。

## 身份与数据边界

已确认的 TOTP 明文保持一致，密文使用子分支的独立密钥重新加密。保留用户、密码、账户、验证状态及验证器锁定状态；清除复制的会话、签名密钥、待用链接和未确认的绑定。复制的 Auth SQL 服务角色在子分支变为 NOLOGIN，子分支使用自己的受限服务角色。

子分支不接受父分支会话 Cookie，也不继承父分支恢复码。未确认的绑定需要重新开始。用户若遗失验证器、仍持有父分支恢复码和账户密码，可在保留的父分支登录后重新读取自己的 TOTP 绑定地址，恢复验证器，再登录子分支。迁移前应保留验证器与父分支恢复资料；删除父分支不能恢复已经遗失的用户资料。

来源验证同时检查物理分支中的安装记录、相同项目和父子关系、成功的来源 Auth 安装历史，以及来源因子密文的认证。凭据重写、会话清除、复制 SQL 登录禁用和原生迁移回执在同一个 PostgreSQL 事务中提交。控制面迁移 059 保存带独立用途 MAC 的不可变结果；原生提交后控制面写入中断时，原 Operation 从原始回执恢复，不再次覆盖用户后来更换的验证器或恢复码。

Auth 状态接口返回 `factor_migration` 汇总。此读取只访问控制面元数据，不查询用户表或唤醒 Compute。客户端不会得到 TOTP 密文、密钥或恢复码。

## 兼容性及范围

加密实现对照仓库锁定的 Better Auth 1.7.7，并使用固定依赖生成的合成向量与真实 PostgreSQL 登录验证。当前单字符串密钥配置输出旧版 hex 密文；不支持其他密钥版本的密文。

稳定根签名密钥仍须保留，在线根密钥轮换没有开放。没有提供控制台管理员绕过用户 MFA 的入口，也没有开放可信设备记忆。备份恢复、外部身份提供商、性能、可靠性及灾备验收不能由本功能的测试替代。

实际部署和物理分支验收见 [2026-10-22 Auth 分支双重认证迁移](DELIVERY-2026-10-22-AUTH-FACTOR-MIGRATION.md)；不能据此推断其余 Auth/恢复功能已完成。
